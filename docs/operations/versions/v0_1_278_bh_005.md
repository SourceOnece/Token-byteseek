## 开发逻辑与依据

代码中的后台连接探针独立构造请求，并不经过 bh.003 的 metadata 快照。因此本轮实际模型测试通过 `/v1/responses`，不能用后台探针代替开关有效性验证。metadata 配置是账号 `extra.codex_metadata_repair_enabled`；修复统一 installation/session/thread/turn/window 标识，当前 body 优先、未知字段保留、只补可信来源和缺省请求 turn/时间，不伪造 sandbox/权限/设备环境。

本次先浏览器登录并确认权限，再创建 0.25 USD 配额、1 天有效且关闭分组回退的测试用户 Key，验证 `/v1/models` 明确含 `gpt-6-astra` 后才发请求。提示词固定要求只回 `OK`、reasoning=low、输出参数上限 128，不调用其它模型。第一轮用整响应读取器，第二轮直接按 SSE 事件读取，以区别 HTTP 200、首输出、终态和客户端超时。

“请求侧 metadata”只使用本测试会话的 session/thread/turn ID 和起始时间，同值放入 `x-codex-turn-metadata` 头及 body `client_metadata`，未伪造 installation/device/sandbox。它不是完整官方客户端 metadata，也不代表管理员修复开关开/关；加入 session 会改变粘性选择，且无法锁定同一个上游账号，不能当作控制变量充分的 A/B。

实现依据：[修复核心](../../../backend/internal/service/openai_codex_metadata_repair.go)、[独立后台探针](../../../backend/internal/service/account_test_service.go)、[用户错误记录接口类型](../../../frontend/src/types/index.ts)。测试脚本仅临时存放在本机，不把密码/JWT/API Key 保存到源码或文档；登录通过无回显 stdin 进入进程内存。

### gpt-6-astra 请求结果

共 8 次串行短文本请求，均明确指定 `gpt-6-astra`、low，未调用替代模型。表中耗时为客户端观察。

| 次序 | 入口与请求侧 metadata | 结果 | 耗时 |
| --- | --- | --- | --- |
| 1 | Responses 流式，无 | 整响应读取器 45 秒超时，未取得最终事件 | 45.0 秒 |
| 2 | Responses 流式，有 | HTTP 200、`response.completed`、模型回显正确、输出 OK | 2.42 秒 |
| 3 | Responses 非流式，无 | HTTP 200、模型回显正确、输出 OK | 4.33 秒 |
| 4 | Chat 非流式，无 | 整响应读取器 45 秒超时，未取得最终响应 | 45.0 秒 |
| 5 | Responses SSE 逐事件，无 | HTTP 200、`response.completed`、OK | 2.20 秒 |
| 6 | Responses SSE 逐事件，有 | HTTP 200 后 `response.failed`，code=`server_error`，消息为服务器 overloaded | 31.95 秒 |
| 7 | Responses SSE 逐事件，无 | HTTP 200、`response.completed`、OK | 3.45 秒 |
| 8 | Responses SSE 逐事件，有 | HTTP 200 后 `response.failed`，相同 overloaded 消息 | 61.40 秒 |

第二轮并未到 90 秒超时阈值，两次都读取到明确失败终态。失败的 `X-Sub2API-Request-ID` 为 `69845702-30d8-4fc2-93c3-090a714ec38e` 和 `53773ef2-d3b7-42c0-9748-6851e9aaaef2`，便于管理员在对应时间窗口定位；普通用户错误列表也出现两条 model=gpt-6-astra、status_code=503 的相同 overloaded 消息。

测试后的用量列表有 5 条该模型成功记录，均为输入 27、输出 5 token，单条 `actual_cost=0.00052`，已记录总消耗为 0.00260 USD。除 4 条客户端明确成功外，另有一条服务端 stream 记录耗时 65,741ms、首 token 31,187ms；它说明客户端超时不等于服务端没有完成/计费，但仅凭现有用户侧记录不能把两个超时分别精确归因。不要把超时全计成 overloaded，也不要把 HTTP 200 全计成成功。

本轮可以确认 overloaded 在该部署仍能复现，以及 Astra 的成功/失败/用量记录链路确实可达；不能确认修复开关是否启用、是否命中同一上游账号，不能据此推导“metadata 必然有用/无用”或修复已彻底解决。

## 发布部署与回退

## 风险与后续同步保留点

没有管理员视角就不能确认选中的上游账号、metadata 开关状态或服务层级；客户端自行带 metadata 与切换服务端修复不是同一个实验。小样本成功不证明过载永不发生，失败需区分认证、分组准入、容量和协议错误。

下一步需要用户提供管理员测试权限或由用户操作指定 OAuth 账号的开关，固定同一账号、模型、tier、出口和并发，比较原始出站 metadata 与终态事件，再测试批量修改后恢复原配置。本轮没有真实 WS 握手/多轮、管理员开关保存和后台批量更新结果，不宣称“完整全站测试通过”。
