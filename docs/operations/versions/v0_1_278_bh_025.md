## 需求与范围

用户要求把双上游同步顺序设为与包豪斯同等长期约束：先看三方差异，先决定采纳 TokenRouter 的哪些更新，再基于该选择后的 ByteSeek，查看本批指定 sub2api 版本剩余的差异；TokenRouter 已吸收且本次会实际进入 ByteSeek 的更新不重复引入。不能只给 sub2api Release 清单，也不能直接按上游版本号大小推断缺失。

本次仅写开发准则、门禁、版本留档要求，不 fetch、合并、改业务、运行真实账号测试、构建或推送镜像。

## 开发逻辑与依据

在 AGENTS.md 设置精简强制门禁，在 operations 中独立定义跨上游的可持续流程，并由开发流程与版本模板引用。比较使用 T0（已采用 TokenRouter）、T1（本批目标）、S0/S1（对应 sub2api 处理范围）、B0（当前本地）、B1（选择 TokenRouter 后的候选/实际本地）这些不同概念，防止把上游已处理误认为本地已拥有。S-target 单列本批 sub2api 目标，避免用户只问一个版本时混入后续版本。

业务来源优先级与实现覆盖分开：授权/反代/模型问题优先审查 sub2api，运营管理以 TokenRouter 为主，但已经适配进入本地的同功能不重复同步；共享调度/计费/TLS 和本地自定义不整文件替换。
