## 需求与范围

用户要求 Metadata 仅作可选修复，不影响其它功能，并询问账号池指纹模式。此前只读审计在禁外网假上游复现：普通 HTTP 同时启用 Metadata 和 session/full 指纹收敛后，最终请求头的 turn ID 与 body 不一致；连接池在 Metadata 开启后把变化的 x-client-request-id 当成硬身份，可能拒绝实际 session/thread 未变的续接。

用户已确认使用现有 Metadata 开关，并要求全范围排查其引入的其它回归。检查 HTTP/透传/Chat/Messages、WS 预热/多轮/续接、指纹组合、重试、换账号、非法与超限输入、API Key/Compact 排除边界，以及单账号/批量保存。不替用户开启 Metadata 或改变指纹收敛，不扩大 API/鉴权/计费/模型/工具策略，不修改线上配置。

## 开发逻辑与依据

HTTP 问题不是网络模拟失败，而是内存 recorder 捕获的最终出站字段不同。Metadata 与旧指纹解析分别生成随机回合 ID；普通 Forward 在 buildUpstreamRequest 之后执行 applyCodexFingerprintHeaders，覆盖了已经修复的 header。末端重新应用不可变 Metadata header，保持所有身份与 body 同源，既不重建模型输入，也不修改旧指纹配置和关闭路径。

连接池继续严格隔离账号、beta/TLS、开关状态及稳定 installation/session/thread/window，只在修复已提供明确 thread-id 且未开启 session/full 时不重复比较 x-client-request-id。全范围审计后收窄了上轮未发布草稿：合并身份时也保留追踪头，避免放宽跨用户连接复用。没有真实线程字段时保留旧追踪号兜底。官方 Codex 通常用 thread ID 填追踪头，故该风险属于头被客户端/代理改变时的兼容问题，不宣称是用户线上报错根因。

来源键只加入实际参与 metadata 构造的字段，不散列整包提示词。除原有 body metadata 和 sessionHint，还包含 prompt_cache_key、推导的 request_kind、身份头、租户 ID、账号 namespace、device/mode/seed。保留同请求内部正常重试的不变性，来源变化则重新构造。缺少 namespace 时不能安全覆盖旧的租户 session 隔离，所以保守返回 nil 让原流程继续；AT 的 bearer 指纹 namespace 仍可用。身份字符校验使用已有 x/net 依赖，不另增依赖版本。
