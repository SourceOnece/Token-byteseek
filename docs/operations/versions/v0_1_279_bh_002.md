### 根因

bh.001 启动时先在 `app/bootstrap` 执行迁移，迁移完成前不监听 HTTP，`/health` 不可用。285 需要为 `usage_logs`（约 166 万行、3.4 GB）整表回填 `platform`，在该库上实测约 3 分钟，没有超出应用 10 分钟的迁移上限。但 Compose 健康检查配置为 `start_period: 30s`、间隔 30 秒、重试 3 次，升级工具在健康检查失败约 90 秒后自动回滚容器，把仍在迁移的进程杀掉。服务端事务在连接断开后回滚；几次重试在服务端相继跑完 `UPDATE` 又回滚，形成约 15 分钟的 WAL/checkpoint 高峰。

280/282/284 已提交而 285 未完成，旧版本随后连接这个半迁移库：它能启动并通过健康检查，但分组、价格和网关鉴权查询失败，因此用户看到页面没有数据、接口 500。数据行本身没有丢失。

### 处置步骤与理由

1. 停止事故状态的 bh.061，避免旧代码继续在不兼容 schema 上读写。
2. 用 `pg_dump -Fc -Z zstd:1` 做全量备份（19:54:32–19:54:58，约 1.03 GB）。`pg_restore -l` 校验出 1361 个目录项、112 张表数据，包含 `providers` 前身 `accounts`、`users`、`api_keys`、`groups`、`pricing_configs`、`usage_logs`、`schema_migrations`。另外保存了 Compose 文件和数据目录（不含日志）。
3. 在应用之外，用 `psql -1 -v ON_ERROR_STOP=1` 单事务执行与镜像构建提交完全一致的 `285_platform_independent_groups.sql`，并在同一事务内写入 `schema_migrations(filename, checksum)`。迁移器的 checksum 是去首尾空白后内容的 SHA-256，我先用同样的算法核对了库中 277–284 共 8 条记录，全部一致后才写入 285 的记录。285 于 19:55:27 开始、19:58:35 提交。
4. 把 Compose 固定为 `0.1.279-bh.001` 后执行 `docker compose up -d`，应用自行执行 286–290 和 Redis 键名迁移，19:59:52 开始监听。

放弃的替代方案：恢复 02:00 或 19:13 的应用备份并回到 bh.061，会丢失备份之后的业务变更；而且应用备份不含用量记录，之后仍要再做一次同样的升级。先改代码、发新镜像再升级，停机时间更长。续跑同一迁移文件不改变任何迁移语义，而且可以校验。

## 风险与后续同步保留点

- 自动回滚与迁移冲突：只要迁移超过约 90 秒，健康检查驱动的自动回滚就会在中途杀掉进程；而旧版本在半迁移库上仍能“健康”运行，但接口 500。后续应另建版本处理：放宽 Compose `start_period` 或在升级时关闭面板自动回滚；迁移期间提供可识别的启动状态；新版本在发现数据库中存在未知的更新迁移时拒绝启动。
- 另一套环境仍停在迁移 266（bh.016），升级会一次执行 267–290。需要先停机并做完整数据库备份，而且不能使用会自动回滚的升级方式。
- bh.061 的备份恢复状态与实际结果不一致，需排查恢复链路的退出码与状态记录。
- 用户在对话中提供过生产 SSH 私钥，应轮换。
- 同步保留点：以后处置同类中断时，只能在核对 checksum 后续跑同一迁移文件，不能手动修改迁移内容或删除 `schema_migrations` 记录，也不能让旧镜像连接已迁移的库。
