## 需求与范围

手动采集不应因为账号 schedulable 关闭而跳过；保持自动采集只对原本可调度账号运行。采集历史支持清空和每条直接删除，按用户明确要求不二次确认。只删日志，不删账号/有效票据/原质量检测或最新状态展示。

## 功能变动

| 功能 | 变动前 | 变动后 |
| --- | --- | --- |
| 停调号手动采集 | 入口及探测/提交都受 IsSchedulable 限制而跳过 | 专用手动 context 只忽略 schedulable，采集开始/重试/提交一致，原对象不变 |
| 自动采集 | 仅可调度独立 OAuth | 不变，仍跳过停调号 |
| 历史批次 | 无删除入口 | 历史每批红色删除按钮、顶部清空全部已结束日志；直接执行、无确认弹窗 |
| 逐条结果/尝试 | 只能查看 | 明细每条直接删除，只影响指定事件；其它明细保留 |
| 活动保护 | 无清理流程 | 活动批次删除禁用且后端409，清空跨全部页面保留活动，结束/失联后可清理 |

账号类型、模型、凭据、禁用/过期/冷却等其余检查及总票据开关不变；采到票不会自动打开调度。原质量测试的启停结果完全不改。

## 开发逻辑与依据

现 collectModel 与共享 probeAttempt 前后都检查 IsSchedulable，须同时拆分手动策略，否则只改入口仍会跳过或不落票。手动标记只在服务端专用上下文设置，自动和用户请求不使用。

历史删除使用已有表、父批次状态锁及级联；不新增迁移。清空不依赖前端可见一页，而按服务器已结束范围执行。活动批次跳过且界面说明；单条删除要求属于指定批次。失败保留前端记录，成功再刷新分页/统计，避免重复点击和旧请求回填。

手动通过 codexTicketManualContextKey 显式设置策略，codexTicketCollectionAllowed 克隆账号结构仅在副本设 schedulable=true，再调用原 IsSchedulable 保留其它字段门禁；共享 probeAttempt 在发请求前和存票前均调用，普通调用无标记仍走原逻辑。测试确认停调号能获得两模型票、最新手动结果仍写原列，真实账号 schedulable=false 且 Extra 不变。

删除 service 使用独立可选仓储接口，handler 校验批次 UUID/事件正整数。Repository 的 CTE FOR UPDATE 锁父批次后检查状态/六十秒心跳；单事件还限定 run_id，不允许跨批删除。清空直接删除已结束/失联父行并利用原 ON DELETE CASCADE 清理关联明细。Heartbeat 发现父行消失返回错误，运行中的旧任务取消，不静默续跑；Append 仅现存running批次可写。最新展示缓存及有效票在 Redis，不由此清理。无实际生产日志删除。

前端把历史卡片拆成详情按钮与独立删除按钮，避免按钮嵌套；顶部清空、每条事件红色按钮都有忙碌/活动禁用。成功才移除/重新读取，当前页清空时回前页；各轮请求版本防旧结果覆盖。未要求删除质量检测历史，本批不扩展过去的质量计划确认规则。
