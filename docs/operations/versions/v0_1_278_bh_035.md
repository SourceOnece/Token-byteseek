## 需求与范围

用户需要多个命名采集代理，轮换定义为同账号/模型未获合格 292 才换下一条重试，固定模式只用指定代理。成功停止、临近过期续采，次数/间隔有界。排查依据是本机保存的回退前快照，不跟随上游撤销功能；程序不能让代理服务商的固定出口自动变动态。功能仍受既有总开关控制，不恢复 Metadata/AT 实验。

用户曾要求结合 [原理文章](https://blog.caowo.de/posts/chatgpt-codex-292-state-anti-degradation-2026/)监控 312；只读核对后明确选择“沿用快照的逻辑”。最终按快照的票据覆盖、缺票模型门控和 TTL 续采实施，不加入文章的业务 312 提前失效逻辑。尚未接通的刷新队列草稿已移除。文章把 292/312 写作状态码/current_turn_state，快照实际判断 HTTP 200 及 x-codex-turn-state 长度；实现以快照为依据，不把文章当作官方质量保证。

## 开发逻辑与依据

代理只写不回显，以 ID 保留已有地址；列表移除先确认再保存。每次保存更换配置代次，旧票据和在途结果不能回写新配置。revision 能拒绝读到已变化版本后的覆盖，不是跨实例原子 CAS；旧版本不能编辑多代理列表。旧 proxy_cipher 镜像保留指定代理，便于回退读取。

采集按账号/模型记录最近代理，成功仍用该代理续采，失败才前移；固定策略失败不换。每次重试前复核凭据/模型/账号资格，使用正常账号并发槽。最多四 worker、轮次三十秒、单次二十五秒，超时可能使实际次数少于填写值。集群轮次使用旧键前缀的 owner 租约，完成只释放自己的锁，崩溃靠 TTL；账号模型租约避免跨实例重复探测。401/403/429 和明确额度/认证/限流/参数错误不为换 IP 而继续当轮，尊重 Retry-After；失败诊断只读 8KiB/1.5 秒并取消该次请求解除阻塞，不存原文。

正常调度的基础/高级/粘性/DB 复核及 WS 模型检查按最终出站模型增加只读票据门控；compact 使用本 fork 原有 compact 映射及兜底解析，不整段替换调度器。HTTP 普通、透传及 WS 头构建器在实际 bearer 和最终模型下复核票据；开启且无票时返回缺票错误，不发合成采集或拼接业务流。有票时移除大小写不同的旧状态键，再写唯一规范头。关闭时所有新增门控/覆盖直接跳过。

票据仍 AES-GCM 加密存 Redis，隔离键包含配置代次、账号、模型、凭据、工作区/组织。Redis 读取失败按缺票处理，并做本实例一秒退避防止逐号等待；设置读取失败则沿原规则停用功能。状态查询只读，不触发采集；blocked 表示模型缺票门控，不表示 schedulable 被修改。

## 风险与后续同步保留点

六秒缺省与多次尝试可能增加上游消耗，管理员可调大间隔。开启后全部缺票会导致对应模型暂无可用账号；关闭功能可恢复原候选/注入行为。覆盖不透明状态头可能影响上游会话表现或缓存，不能据单测保证无影响。按快照不监控业务 312，因此 TTL 尚未到时不会因该信号提前失效；这是用户最终选择。动态代理实际出口由服务商决定。后续同步保留可选开关、有限采集、私有加密/隔离、多代理失败切换、质量检测与模型门控独立、包豪斯；不得恢复 Metadata 或新 AT 实验。
