## 需求与范围

用户要求完整跟进 TokenFlux，保留 UI/包豪斯、票据等定制功能；sub2api 只作增量。这个目标取代此前长期只选小修复的同步策略，但不表示“删除本地定制再换原版”。本版完成规则调整和迁移影响审计，没有用规划冒充已完成应用迁移。

本次按推荐方向评估：接受 TokenRouter 新 Provider、跨平台分组和统一价格后台作为目标结构；旧账号、历史计费和票据数据必须通过可验证迁移保留。票据、质量检测、STATE、代理、异常守护和调度联动要重新接入新运行链，不能只留下旧文件和页面。

## 开发逻辑与依据

审计固定三方 SHA 后，对比 Git 树、真实 SQL 和本地票据调用。相对 T1 为 129 个本地侧/283 个上游侧非共同提交、约 8442 个文件差异；其中包含 merge、代码搬迁、生成代码和已等价移植的补丁，不能解读为“缺 283 个功能”。

TokenRouter S00–S16 把旧 handler/service/repository 拆到 provider、gateway、scheduler、billing、routing、egress 等模块。完整跟进必须迁移本地扩展的所有者，而不是保留旧服务、让新请求绕开票据。

| 本地保护项与现行路径 | 新结构中的接入要求（待实施） |
| --- | --- |
| `service/codex_ticket_service.go` 依赖旧 OpenAIGatewayService 的账号仓储、访问令牌、HTTP/TLS、并发、调度摘要 | 独立票据服务使用窄接口访问 provider/egress/scheduler，由 app 统一装配和启停 |
| `codex_ticket_probe/verify_probe`、`validation`、`watchdog` | 动态采集与固定业务代理复验分开；同账号/模型完整终态匹配；STATE 仍保密，业务请求继续注入和观察 |
| `codex_ticket_scheduling`、`actual_filter`、`gateway_service` 的票据资格错误 | 新选号与发送前都查票；合格开、明确降智关、其它不变；503 有界换号和调度摘要补全不能丢 |
| `codex_quality_service/schedule`、对应 repository | 原题目、关键词、模型/协议/思考配置、定时历史、失败不关调度和满血统计接入新的 provider 测试/管理链 |

| `repository/codex_ticket_*` 和质量表 | 账号 ID 不重编号，外键和调度更新 SQL 适配 renamed table；保留历史和缓存隔离 |
| 管理 handler 与前端账号/设置/仪表盘 | 原勾选批改、共同值/空值、实际长度筛选、模板、邮箱列、时间/IP/响应模型和统计不丢 |
| 已从 sub2api 补入的 MiniMax/OpenCode、Images、协议修复 | T1 provider/routing 不自动包含这些本地增量；迁移后补入真实执行、目录和用量链，不能倒退 |

## 风险与后续同步保留点

- 完整 TokenFlux 跟进不是简单 cherry-pick；需要先把票据和质量检测接到新 provider/gateway/scheduler 运行链，再开放上游迁移。
- 上游删除旧字段时不能静默提高价格、删除额度或丢历史；每个迁移必须有归档、冲突检查和回退边界。
- 后续新增变化仍固定 SHA；任何“已同步”都要有实现提交、运行路径和测试证据。
