## 需求与范围

后台系统设置“功能开关 → 团队功能”增加邀请限流自定义。默认保持同团队同邮箱 60 秒间隔、每团队每小时 20 次。只改变邀请和重发的限制参数，不影响成员权限、邀请 token、SMTP、其他发信场景或上游账号。

## 功能变动

| 功能 | 之前 | 本次 | 入口 |
| --- | --- | --- | --- |
| 同邮箱邀请间隔 | 固定 60 秒 | 可设 1–86400 秒，默认 60 | 管理员团队设置 |
| 团队每小时总次数 | 固定 20 | 可设 1–10000 次，默认 20 | 同团队所有邮箱/邀请与重发合计 |
| 运行时生效 | 需改代码 | 保存后无需重启；已有 Redis 计数和冷却保留 | TeamService → limiter |

## 开发逻辑与依据

在 settings 表保存两个独立数值，管理 GET/PUT 回传，旧请求省略则保留原值。每次邀请/重发批量读取两个设置并传入 Redis 原子脚本，读取失败拒绝发送，缺失/无效历史值回退旧默认。前后端校验正整数和上限，0 不代表无限制。

已有邮箱冷却 key 按原 TTL 到期，下一次允许发送后使用新间隔。小时窗口仍从首个允许请求起计一小时，修改上限不清空次数也不重置窗口；提高上限立即用于下次判断。发信前计数、失败仍可能占次数、被拒不延长窗口均沿用原规则。

## 上游同步与保留差异

无上游合并；保留包豪斯、共用名称邮箱搜索、质量检测和固定版本镜像发布规则。后续同步注意不能恢复固定邀请参数。

## 包豪斯适配

原团队卡片内新增网格输入，复用 input/label、蓝/黄重点标签、硬边框和主题色，其他功能卡片不变。桌面两列、手机单列；原团队开关关闭时禁用新输入并保留数据，字段焦点沿用公共样式。1440×1000 与 390×844、浅色中文/深色英文、减少动画检查均通过，没有页面溢出。

## 接口数据与兼容性

既有管理设置 GET/PUT 增加 team_invitation_cooldown_seconds、team_invitation_hourly_limit。公开设置不新增字段。无需迁移/依赖/重启；新站默认值与升级缺键回退均为 60/20。旧客户端省略字段不覆盖管理员值；不改变团队邀请 HTTP 路径或错误码。
