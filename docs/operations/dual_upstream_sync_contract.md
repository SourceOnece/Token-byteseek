# 双上游差异优先与去重同步契约

本文是 ByteSeek fork 的长期同步约束，与[包豪斯设计契约](bauhaus_design_contract.md)同时生效。适用于上游咨询、差异评审、移植、同步及相关开发，不授权自动部署。用户在 bh.064 阶段明确将目标调整为：TokenFlux/TokenRouter 主线完整跟进，保留包豪斯和 ByteSeek 定制功能，sub2api 去重后增量补充。固定顺序仍是：固定三方基线 → 对齐 TokenRouter → 接入本地保留能力 → 以实际结果核对 sub2api 剩余差额。

## 来源分工与边界

2026-09-29 用户进一步明确：以 TokenFlux 最新实现为基底，再附加 ByteSeek 定制和 sub2api 去重增量。上游已替换的通用设计（如跨平台分组、共享价表、平台额度下线）采用新方案，不为原 TokenFlux 旧行为额外实现长期兼容业务。数据库升级仍需归档、验证和说明；保留历史数据不等于继续执行旧逻辑。票据、质量检测、包豪斯及用户明确新增的能力不因此删除。

2026-10-01 再次明确：非定制的通用功能继续按 TokenFlux 现行方案，包括上游撤除的价格批量模型填充入口、统一目录和模型 ID 语义；不能仅因本 fork 以前暂缓而长期保留旧实现。包豪斯保护约束呈现，不豁免同一 UI 提交中的功能、可访问性和生命周期修复。sub2api 增量按实际缺口接入新主体，不恢复已撤回的实现或绕过新目录/路由所有权。

同日 bh.002 的后续授权进一步明确：直接跟进 TokenFlux 页面布局及动效，默认 TokenFlux 皮肤，包豪斯通过管理员设置页统一选择，普通用户与访客没有皮肤切换入口（bh.003 纠正）。不得再以旧包豪斯布局为由跳过上游 UI 功能、规则编辑器、加载保持、键盘可访问性与过渡生命周期；自定义业务组件叠加到同一套页面，两种皮肤不分叉 API 或业务策略。bh.004 用户明确保留包豪斯旧首页构成，作为 /home 的展示例外；数据、精选模型、公开配置和登录仍复用当前实现，TokenFlux 首页不回退。

1. ByteSeek 是最终集成主线；TokenFlux/TokenRouter 是直接上游，Wei-Shaw/sub2api 是第二层上游。每批核对实际仓库和引用，不用版本号大小猜测继承关系。
2. TokenRouter 是目标架构和通用功能的主体。不能仅因本地缺少同名模块、改动规模大或曾在旧批次暂缓，就永久排除其有效更新；应规划迁移、接口适配和验证。账号授权/凭据刷新、反代传输、模型/协议能力的剩余缺口再参考 sub2api；图片上游协议保留用户明确选择的 sub2api 方案。来源优先级不是盲目整文件替换，也不证明旧价格/配额可以无损转换。
3. 调度、分组准入、会话/缓存隔离、模型映射、TLS 和计费连接多个模块，须共同验证。不能以“反代来自 sub2api”为由覆盖 TokenRouter 的订阅结构、调度器或本地 UI。
4. 包豪斯、邮箱列/共用搜索、质量检测/定时任务、票据工作台、账号规则/导入默认值/勾选批改、动态与轮换代理/IP 复用、双链路复验、STATE 注入、异常守护、三态调度联动、管理员真实响应模型记录，以及其它仍有效的定制均为保留项。新架构上线前必须重新接入真实业务路径，不能只保留旧文件和界面。明确撤回的功能（例如 Metadata 补齐实验、Bearer 生成 AT）不能从任一上游重新引入；恢复须先说明并取得用户授权。
5. 用户只让“先看区别/能否合并”时只读报告，不实际合并、推源码、打包或部署。用户明确授权实施时在该范围内推进，新增依赖超出范围须先确认；本规则不替代授权。

“完整跟进”与“代码逐字一致”不同：UI 按包豪斯重做，新模块接入本地扩展，重复修复去重；上游删除旧字段时核对数据用途。可等价转换的旧配置迁移到新结构，不能等价的收费、配额或公开接口行为必须给出具体差异和处理选择，不可悄悄删值或提高价格。

## 固定比较基线

每批开始固定以下信息，记录查询日期/时区、Release tag 与实际 commit；过程中上游有新提交，不能悄悄移动目标。

| 标识 | 含义 |
| --- | --- |
| B0 | 当前 ByteSeek HEAD、应用 VERSION、已采用上游及本地额外/撤回项；运行镜像单独记录，不假定 HEAD 已部署 |
| T0 / T1 | 上次实际采用 TokenRouter 的基线 / 本批拟评估的固定目标 SHA |
| S0 / S1 | 对齐 T0/T1 的 sub2api 同步处理边界，不代表其中功能全部采纳 |
| S-target | 本批 sub2api 目标版本/SHA；可等于 S1，或为用户要求的后续版本 |
| B1 | B0 加上本次选定 TokenRouter 更新后的候选/实际状态；未实施时只能称“预期 B1”，不能称已合并 |

Release、主线与 VERSION 回写分别记录，TokenRouter 与 sub2api 的版本号不能直接换算。merge-base、祖先关系和同步记录仅用于定位待审范围；“mark processed / skip / preserve tree”等提交可能只是记下已审查或跳过。必须检查补丁、最终代码和测试，才能判定实际覆盖。T0 或 S0 无法完整确定时明确列出不确定范围，不猜测基线。

本契约不保存会过时的“最新版本对照表”；每批报告/版本记录保存当时固定基线。

## 两阶段决策

### 第一阶段：先决定 TokenRouter 同步什么

1. 列出 T0 → T1 的功能级更新，对照 B0。初始 PR、后续修正、测试、上游撤回作为完整变更链评估，不把已撤销的初稿当候选。
2. 标注本地已有、部分覆盖、待采纳、需要适配、保护项冲突或待核实，说明来源、作用、依赖与影响。用户已授权完整跟进的批次默认纳入目标中的通用功能和架构，不重复逐项询问；涉及无法等价迁移的重要业务选择才需确认。
3. 冻结清单形成预期 B1；真正实施后记录实际 B1。尚未迁移和验证的模块仍是待完成，不能以“已处理”或整体 merge 标记宣称完整同步。过去暂缓不等于用户永久拒绝；明确撤回的功能仍依第 4 条保护。

### 第二阶段：再决定 sub2api 还补什么

1. 针对同批 S-target，同时比较 sub2api、T1 和 B1，不能只将最新 sub2api 与未对齐的旧 B0 比较。
2. S0 → S1 范围核对 TokenRouter 引入、适配、部分覆盖及主动跳过项；S1 → S-target 的更晚增量单列。用户只指定一个版本区间时，不夹入范围外功能。
3. T1 已实现且选入 B1 的同等行为，标为“随 TokenRouter 获得，无需重复同步”；B0 独立实现的等价功能也不再引入。剩余缺口才成为 sub2api 补充候选。
4. TokenRouter 主动跳过或本次没选的项目须说明原因，不能把“未覆盖”变成自动采纳。用户已拒绝的行为不得换 sub2api 来源绕过选择；实现不同且值得重新评估时先说明差别并确认。
5. 第一阶段落地后以真实 B1 再去重；第二阶段完成后复核 TokenRouter 采纳项和本地自定义仍有效。选择、目标或依赖改变时重算受影响项，不沿用失效结论。

## 覆盖判定与去重

判断单位是最终有效行为，不只是提交 SHA、文件名、模型名或标题相同。

| 情况 | 处理 |
| --- | --- |
| 原提交进入 B1 且行为仍存在 | 已覆盖，不重复补丁或迁移 |
| TokenRouter/ByteSeek 用不同 SHA 适配等价功能 | 核对调用链、默认值、错误边界和测试后标为等价覆盖 |
| 同步记录标已处理，但明确 skip 或最终树无实现 | 已处理但未覆盖，列出跳过原因，不冒充本地支持 |
| 仅覆盖部分账号类型、协议、界面或异常路径 | 部分覆盖，列清剩余差额；例如网关接通不代表工作台接通 |
| T1 有，但没有被本次选入 B1 | 上游有、本地仍缺，列明未采纳原因，不能当成已同步 |
| B0 已先从 sub2api 移植，后来 T1 又带回 | 第一阶段也要去重，比较后续修正，只引入尚缺差额 |
| 上游/本地后来撤回或替代 | 以最终意图为准，不按祖先关系恢复旧行为 |
| 缺源码或证据不足 | 待核实，不宣称等价、可安全合并或已实现 |

Git cherry/patch-id 可辅助识别同补丁，但模块路径、重命名和适配可能影响识别。Git 无文本冲突只表示能拼接，不证明业务兼容；有共同祖先也不证明 feature 的最终运行分支存在。

每项维护来源映射：sub2api 原 PR/SHA → TokenRouter 对应引入/适配/跳过 PR/SHA → ByteSeek 已有或本次落地 SHA。记录未覆盖与后续修正，不用虚构 SHA 填空。来源和决定放在当批版本记录；SYNC.md 仍仅作本机进度，不提交。

## 差异报告

报告先给三方基线及“会新增什么、哪些不用重复”，再给必要证据，至少包括两张表：

**TokenRouter 选择清单**

| TokenRouter 功能 / PR、SHA | B0 现状 | 变化、依赖、风险 | 建议 / 用户决定 | B1 覆盖方式 |
| --- | --- | --- | --- | --- |
| 本批填写 | 已有/部分/没有/撤回 | API、UI、缓存、调度、计费、迁移影响 | 引入/适配/跳过/待确认 | 保留/预期引入/未选，实施后补真实 SHA |

**sub2api 剩余差异**

| sub2api 功能 / 版本、PR、SHA | T1 处理及证据 | B1 预期/实际覆盖 | 是否还需同步 | 依赖、风险、验证与决定 |
| --- | --- | --- | --- | --- |
| 本批填写 | 直接/等价适配/部分/跳过/无/未知 | 已有/随 T 获得/仍缺/用户拒绝 | 无需重复/仅补差额/适配/不采用/待确认 | 明示原因与未测范围 |

未选、主动跳过、延期和待核实项也保留原因，不能只记录成功项。只读报告不新增版本；产生持久变动则按[版本规则](version_history.md)留档三方基线、映射与最终决定。

## 实施验证与交付

- 在授权清单内先 TokenRouter、后 sub2api 补差额；不同时整仓混合使来源难以追溯。不为分析/编号创建或切换分支、改 VERSION、建 tag。
- 迁移先查本地是否已有等价数据变更；已有则不重复执行，确需新增时从当前最大 ID 递增，保留依赖顺序和非事务标记，修复引用，不改已发布迁移。
- 共享链路须验证多账号切换、不同用户/API Key/线程隔离、额度耗尽、模型/协议准入、计费不重复及质量检测联动。上游测试通过不等于在 ByteSeek 通过。
- 新增/修改界面按包豪斯统一，保留公共组件、硬阴影及交互状态；视觉修改不顺带改变业务。服务端新能力、后台账号测试和用户工作台分别检查，未接通路径明示。
- 更新当前工程文档及版本记录，区分单元/mock、真实测试、未测及部署状态。纯文档或只读比较不打包镜像；应用发布沿用固定标签、latest/bauhaus 同产物及单独部署授权。
