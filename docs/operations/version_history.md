# 版本留档规则

本文定义从 2026-09-06（Asia/Tokyo）起每次持久变动的历史记录要求。版本记录回答“为什么改、怎样实现、改变了什么、如何验证和发布”，不以提交标题代替说明，也不要求记录私人推演过程。现行架构/接口/设计契约仍维护在对应 Project Doc 专题，重要架构决策另用 ADR。

## 交付单位与编号

1. 任何持久变动均须留档：功能、修复、重构、UI、上游合并、配置/依赖、部署/回滚、文档/约束。只读咨询和无持久变更的检查不新增。
2. 一次围绕同一目的的交付对应一份记录，可包含多个代码提交和验证修正，不为每次编辑或临时生成物建版本。交付冻结后再作功能变动，即使上游版本不变，也另建修订。
3. 文档标识使用 `v<上游版本>-bh.<三位递增序号>`，例如 `v0.1.278-bh.001`；文件名为 `v0_1_278_bh_001.md`。同一上游版本取历史最大序号加一，上游版本变化时从 `001` 开始，前序交付通过链接串联。
4. 这是 fork 历史标识，不是应用 SemVer，也不是 Git tag。不得为纯文档留档修改 `backend/cmd/server/VERSION`、API 版本或创建 tag；应用真实版本、上游 SHA、源码 SHA 和镜像 digest 单独记录。
5. 文件放入 `docs/operations/versions/`；[历史目录](versions/index.md)按最新交付优先规范列出每篇记录和读取时机。[统一模板](versions/template.md)不占版本编号。

## 开始到交付

1. 读取仓库约束、根目录、当前规则、历史目录中的最近记录和相关模块旧记录；对上游同步确认 fork 与 upstream 基线。
2. 动手前从模板创建记录草稿，填需求、边界、前序版本、预期功能差异和保留项。它是版本记录，不替代计划模式要求的 `.agents/plans/`。
3. 实施中维护实际实现理由、关键路径、变更前后行为和验证结果。方案调整写清最终选择及被替代原因，不抄全部聊天/调试流水账。
4. 交付前核对实际 diff：每个功能/行为改动均能在记录中找到归属；未改项明确写“不涉及”并解释，重要未测项明确列出。同步当前工程文档及历史目录。
5. 记录随实现提交，未解决问题不能标为通过。若工作确实被阻断，将草稿标成阻断并写原因；恢复同一交付时继续，不伪造已发布。
6. 测试和包豪斯验收通过后才发布应用镜像，再追加真实发布证据；纯文档交付完成文档检查即可，不因没有 UI 变化而改 UI 或重打相同镜像。

## 完整记录内容

每份记录都保留模板全部栏目；不适用时说明原因，不能删除栏目逃避审查。

| 栏目 | 必需内容 |
| --- | --- |
| 元数据与边界 | 文档 ID、带时区日期、交付类型/状态、前序记录、上游版本/SHA、fork 起点、实现提交定位、范围与明确不做的事。 |
| 需求和功能差异 | 用户目标、原问题；按功能给出变动前后行为、受影响角色/页面/入口；区分上游引入与 fork 自定义。 |
| 开发逻辑 | 方案和选择理由、关键模块/调用或状态变化、数据和配置来源、异常/回退处理、重要替代方案及取舍。细节以本次改动为边界，不把整仓库复制进记录。 |
| 代码与同步依据 | 关键文件/符号、对应提交/测试；上游范围、冲突和解决依据、保留的 fork 差异、未来同步不得覆盖的约束。没有合并时写清基线未变。 |
| 包豪斯适配 | 使用的公共组件/token、页面/控件/动效、业务语义色、移动与深色状态；纯后端/文档交付说明不涉及，并确认不改变已有设计。 |
| 契约与兼容性 | API、鉴权、计费、数据结构、依赖、配置和迁移影响；新增迁移的 upstream→fork 编号映射；无变化要基于 diff 核实。 |
| 验证 | 命令/用例或可复核操作、目标提交和环境、通过/失败/未运行、覆盖范围与限制；截图/日志有稳定位置则链接，没有则保留文字证据，不能只指向临时 `/tmp`。 |
| 发布与运维 | 是否构建/推送/部署分别记录；源码 SHA、应用版本、平台、双标签 digest、隔离/真实检查结果；跳过原因、旧产物和迁移恢复边界。 |
| 风险和后续 | 未解决风险、后续工作、回退约束、未来同步保留点；任何回滚再建记录并链接被回滚版。 |

## 提交和发布证据

- 包含实现的提交也包含当时已知的版本记录。记录不能包含自身提交的最终 SHA：采用已知父提交 + `git log -- <版本文件>` 定位；提交后可追加实现 SHA，禁止猜测或为嵌入自身 SHA 循环 amend。
- 每次应用发布增加固定 fork 版本标签，格式为文档 ID 去掉前导 `v`，例如 `ghcr.io/sourceonece/byteseek:0.1.278-bh.018`。纯文档修订不创建应用镜像标签，不为标签修改应用 VERSION 或创建 Git tag。
- 版本标签按发布流程禁止覆盖：推送前查远端，已存在且 digest 相同则跳过，存在但不同则停止并采用新版本号。验证候选后先推版本标签，再将同一产物发布到 `:latest` 和 `:bauhaus`；核对三个远端清单 digest 相同才算发布完成。`latest` 始终代表最近成功发布的应用，`bauhaus` 为兼容别名。
- 版本标签不等于注册表技术锁定。严格固定产物使用 `镜像名@sha256:清单digest`；记录清单 digest、镜像配置 digest、平台和源码 SHA，不能把配置 digest 当成可拉取清单 digest。
- `latest` / `bauhaus` 会移动，不能单独充当历史依据。保存不可变的 `ghcr.io/sourceonece/byteseek@sha256:…`、构建架构及代码 SHA，旧应用仍须遵守数据库兼容性才可恢复。
- 打包前完成开发和验证栏目；构建/推送后以仅文档提交补记 SHA、digest 和结果，不为这次证据补录再建版本或重新构建。镜像源码 SHA 仍指向真正打包的提交，不冒充补录后的文档提交。
- 纯文档/约束改动独立留档，但不重打镜像；记录最近已发布镜像只作参考，并注明它不包含本次文档。镜像发布与线上部署分别获得证据，未经单独上线授权不替换运行容器。

## 历史修订与安全

已完成记录保存当时事实，不随现行实现重写。只允许追加发布证据或注明日期、原因和证据的勘误；后续需求、回滚、替代方案另建记录并链接旧版。补录旧版必须标为补录，区分 Git/发布证据可证实内容和无法核实内容；本次基线之前不承诺完整历史。

不存储密钥、OAuth token、auth.json、Cookie、客户/生产数据、内部私人联系方式或含秘密的完整配置与日志。使用脱敏字段、合成样例和可公开的提交/镜像标识。

## 同步时如何使用

双上游批次必须按[去重同步契约](dual_upstream_sync_contract.md)先确定 TokenRouter 采纳项，再对选择后的 ByteSeek 核对 sub2api 剩余差异。记录当前/目标三方 SHA、TokenRouter 对 sub2api 的处理边界、用户选择、直接/等价/部分覆盖、跳过与撤回原因及原 PR 到本地提交映射；未实施的预期覆盖不能写成已同步。后续 TokenRouter 带回已从 sub2api 移植的补丁时，读取这些映射避免重复代码或迁移。

从最近版本的“后续同步保留点”定位相关旧记录，再核对当前代码及设计契约。上游修复、fork 自定义、已淘汰规则分别判断；有历史记录不能代替 diff 和测试。若旧记录与现行契约冲突，核对后续替代版本和用户授权，不能静默恢复旧版行为。
