# ByteSeek 正式版 bh.026 到 bh.030 的完整变化说明

> 这是一份只读说明，不包含代码修改，也不代表要重新部署。
>
> 说明范围：正式镜像 `v0.1.278-bh.026` 到当前发布的 `v0.1.278-bh.030`。
>
> “上游最新”在本文中指本批固定核对的快照：TokenRouter `v0.1.278`、sub2api `v0.2.5`。上游之后的新提交不在本次比较范围内，不能把本文当成今天远端仓库的实时状态。

## 先看这里：小白版结论

### 三个词是什么意思

- **完整同步**：上游功能已经在 ByteSeek 里可以直接使用，入口和作用基本一致。
- **兼容适配**：功能已经有，但为了不破坏你的多账号池、原有计费、复合 Key、订阅或包豪斯界面，ByteSeek 用自己的方式接入。对用户来说能用，但代码不一定和上游一模一样。
- **未同步**：当前没有加入。不是漏做，而是这个功能会改变账号池边界、需要 ByteSeek 没有的数据结构，或者上游自己已经撤回。

### 你最需要记住的配置原则

1. **不配置就不会突然改变旧行为**：模型白名单、图片 Base64、推理倍率等新能力默认不会擅自打开。
2. **账号池功能大多自动执行**：额度切换、429 冷却、WS 隔离、质量检测不需要逐个用户配置。
3. **模型白名单是唯一要特别小心的开关**：打开后会真的拒绝未列出的模型，建议先在一个测试分组开启。
4. **MiniMax/OpenCode 不要直接全量入池**：先加少量账号，做连接测试和质量检测，再加入正式分组。
5. **批量订阅结果不明确时不要换新键重试**：先查用户实际订阅，避免重复发放。

### 这些东西不是设置项，而是程序内部保护

下面这些没有后台开关，是为了保护中转站稳定性：

- WebSocket 连接池和会话隔离；
- 429 和额度窗口判断；
- 账号切换、失败释放和有限排水；
- 兑换码固定时间窗口；
- 支付订单锁和金额复核；
- 模型单项查询的权限过滤；
- 备份和数据库迁移互斥锁。

你不需要为了“开启同步”再去找开关。

## 一句话结论

bh.026 已经是一个可用的包豪斯版网关，重点是 Codex 图片、WebSocket 稳定性、缓存、请求 ID 和额度窗口。

从 bh.026 到 bh.030，主要增加了四类能力：

1. 更多模型和协议：Astra、Opus 5、Bedrock、Ultrafast、MiniMax、OpenCode Go/Zen，以及更完整的图片和协议兼容。
2. 更安全的号池和调度：模型白名单、Ollama 限流、缓存同步、账号质量/连接状态处理、WS 会话隔离。
3. 更完整的管理后台：批量订阅、批量分配、批量编辑 Key、代理维护、模型目录、供应商筛选和停用分组处理。
4. 更稳的支付、认证和运营：支付补偿、兑换限流、登录容错、站点销售模式、价格和用量展示修复。

这些更新没有恢复已撤回的 Codex Metadata 补齐，也没有恢复 Bearer Token 生成 AT。绝大多数新开关默认不改变旧行为。

## 第一部分：从 bh.026 到现在新增了什么

下面按“用户能感知什么”和“为什么做”解释。

### 1. OpenAI/Codex 模型能力增加

#### GPT-6 Astra

现在支持 Astra 的专用推理模式、指令模板、缓存和失败重试边界。

通俗说：Astra 不能完全按照普通 GPT 的请求格式处理。现在系统会识别 Astra，使用它需要的指令和推理字段；出错时只在允许的范围内重试，不会把普通模型的参数硬套过去。

这样做是为了避免 Astra 被错误降级、错误计费，或因为普通模型规则导致请求失败。

#### Opus 5 和 Bedrock

增加 Opus 5 的模型 ID、区域/全球 Bedrock 路由和价格映射。

通俗说：同一个 Claude/Opus 模型可能要走不同区域或 Bedrock 入口。现在系统会按配置选择正确的上游，不会把区域 ARN 当成普通模型名处理。

#### Ultrafast 和推理计费倍率

增加 Ultrafast 服务等级的识别，并支持渠道级可选推理倍率。

重要默认值：

- 没有配置倍率时按 `1` 处理，不会自动加价。
- 没有自动把 Fable 之类的模型乘以 3 倍。
- 旧 Fast/Standard 价格和既有账单不回写。

这样做是为了让新计费能力可以配置，但不会突然改变你现有用户的价格。

#### 模型目录和单模型查询

现在除了模型列表，还支持查询单个可见模型：

```text
GET /v1/models/{model}
GET /models/{model}
```

返回的模型必须已经通过：

- 分组权限；
- 账号可调度状态；
- 渠道模型映射；
- Key 别名；
- 模型白名单；
- 复合 Key 前缀和订阅范围。

通俗说：用户不能通过单模型接口绕过号池权限，随便探测或调用分组外模型。

管理员模型选择器也不再把 MiniMax/OpenCode 错误显示成 Claude 默认模型。

### 2. Images 图片能力比 bh.026 更完整

bh.026 已经有 Image 2.5 的基础原生能力；之后补齐了 Image 1.5、Image 2、Image 2.5 的更多生成/编辑/流式场景和测试。

当前逻辑大致是：

- 适合原生 Codex Images 的模型走原生生成/编辑接口。
- 旧模型继续走原有 Responses 兼容路径。
- 只有上游明确返回 404/405 时才有限回退到旧路径。
- 普通 401、429、5xx 不会被伪装成协议不支持。
- 创作台、账号测试、普通网关使用同一套图片判断。

另外增加了 OpenAI API Key 的可选 URL 转 `b64_json`：

- 默认关闭；
- 只处理非流式 URL 结果；
- 失败时保留原 URL，不让主请求失败；
- 限制下载大小和时间；
- 阻止私网重定向、URL 用户信息和 HTTPS 降级；
- 不携带账号凭据去下载图片。

这样做是为了兼容一些只接受 Base64 的客户端，同时避免图片回填变成 SSRF 或额外计费入口。

### 3. Responses/Chat/Anthropic 协议兼容更完整

#### Responses 终态和工具恢复

现在能处理更多上游只在 `done` 或终态事件中返回的文本、工具参数和调用 ID。

通俗说：以前有些上游把内容放在最后一条事件里，网关可能只转发增量，导致用户看到半截答案或工具参数为空。现在会在不重复内容的前提下补齐。

#### additional_tools 和 agent_message

Responses Lite 的特殊工具命名空间、Codex 子智能体任务文本和 Chat 转换都做了兼容。

这不会给普通用户凭空增加工具权限，只是避免协议桥转换时丢字段。

#### Responses 转 Chat 的 system 消息

只有 Responses 转 Chat 的兼容桥会：

- 合并开头的 system 指令；
- 将中途不被目标上游接受的 system/developer 内容降为 user。

原生 Chat 和原生 Responses 不改变。这个取舍是为了兼容严格的 Chat 上游，但它不等价于保留原始 system 权限语义。

#### Claude Code 兼容

增加了 thinking block binding、消息级 output_config、CLI 探测和默认 Header 对齐。

`max_tokens=1` 的 CLI 探测不再只允许 Haiku。未知正文块会保留，不会因不认识就静默丢掉。

### 4. WebSocket、长流和账号池更稳

这是从 bh.026 延续并进一步修正的一大块。

#### 连接池常驻读取

后台会持续读取上游 ping、关闭帧和控制事件，避免连接看似空闲但实际上已经坏掉。

#### 会话隔离

WS 会话现在按更明确的执行域隔离：

- API Key；
- 用户/线程；
- 请求类型；
- continuation/previous response；
- TLS 指纹和握手能力。

通俗说：一个用户或一个账号的会话状态不会因为连接池复用，被另一个用户、另一个 Key 或另一个账号抢走。

#### 客户端断开后的有限排水

客户端断开后，网关在有限时间内继续读取已经发出的上游结果，以记录真实用量；不会无限等待、不会把请求重放到另一个账号。

#### 失败释放和后续轮次

没有实际服务用户请求的失败会话会释放槽位；后续轮次错误可以触发重连或换号，但不会把第一轮请求重复发送。

### 5. 429、额度和调度修复

- 普通 429 且额度没有耗尽时，不会错误地长时间停用账号。
- 只有确认额度窗口耗尽，才按重置时间调度。
- Codex 5 小时/7 天窗口按窗口长度识别，不再把 primary/secondary 错配。
- 账号的运行时封禁状态增加代次/CAS 保护，旧请求不能覆盖新状态。
- WS 会话模型字符串使用原子读取，修复并发竞争。
- 质量检测结果继续影响调度：降智/失败账号不会被当作满血账号使用。

### 6. 新增 MiniMax 平台

新增 MiniMax 平台，包含：

- API Key 账号创建/编辑；
- Pay-as-you-go 和 Coding 模式；
- Chat、Responses、Anthropic 兼容入口；
- 模型预设；
- 用量读取；
- 额度窗口和调度快照；
- 管理后台平台图标、颜色和模型配置。

Coding 用量只接受格式正确的官方剩余额度；异常数据不会被当成“100% 满血”。Payg 模式不会伪造余额。

### 7. 新增 OpenCode Go/Zen 平台

OpenCode 现在分成 Go 和 Zen 两种模式，支持：

- 三种入口协议映射；
- Go/Zen 不同的默认模型和协议规则；
- Chat/Responses/Messages 的模型转换；
- API Key 账号测试；
- 统一只读用量查询；
- 额度和监控；
- 管理后台创建、编辑和自定义端点；
- 自研规则编辑器，不使用原生 select。

会话 ID 会按 Key、账号、凭据和客户端会话隔离，并对自定义端点做哈希处理，不把原始地址当作会话 ID。

### 8. 可选的分组模型白名单

新增独立的 `model_allowlist`，与旧的“模型展示列表”分开。

默认关闭，所以升级后不会自动限制模型。

开启后，HTTP、WebSocket、创作台、批量图片和复合 Key 都会检查最终模型。别名、映射、前缀会在正确的阶段检查，避免把内部映射名称误当成用户请求名称。

这样做的原因是：旧模型列表只是“展示什么”，不能直接改成“禁止调用什么”，否则升级会突然拒绝旧用户请求。

### 9. 后台和运营功能

#### 订阅批量操作

管理员现在可以批量：

- 增加/减少有效天数；
- 重置额度窗口；
- 撤销；
- 恢复。

每个订阅独立事务，某一条失败不会回滚其它已成功项。

#### 多用户分配同一套餐

订阅分配弹窗仍默认单用户；勾选批量后可以选择最多 100 个用户。

系统会：

- 去重用户 ID；
- 保留原套餐时间链；
- 已有同套餐时追加 pending，而不是覆盖；
- 使用幂等键防止重复发放；
- 结果不明确时冻结原用户、套餐、天数和操作键；
- 部分失败后只保留失败用户。

这不是跨进程 exactly-once 任务系统。如果进程在数据库提交后、结果保存前崩溃，不能直接换新键重试，必须先检查实际订阅状态。

#### API Key 批量编辑

支持当前页面多选和显式字段勾选。部分失败只重试失败项，复合 Key 不允许批量改单分组，避免破坏多分组绑定。

#### 账号和分组管理

- 账号编辑可以看到并移除仍绑定的停用分组。
- API Key 创建增加 Anthropic/OpenAI/国产/其他供应商筛选。
- 筛选依据真实平台，不依据管理员自定义名称。
- 复合 Key 编辑不受创建筛选影响。
- 用户搜索、邮箱链接、已删除用户历史查询保持原语义。

#### 代理维护

代理编辑区分“没有提交”“显式 null”和“空字符串”：

- 没提交：保持旧值；
- null/空字符串：按字段规则清除；
- 只改名称或状态：不会意外清掉凭据、备用代理或有效期。

备用代理改成有向关系，支持多个代理指向同一备用代理；重复过期回退会保留最初来源。

#### 备份和迁移

数据库 dump 会和迁移使用同一把 advisory lock，避免备份读取到半迁移状态。连接异常会被丢弃，不复用坏连接。

#### 登录和认证容错

- JWT/Admin 临时数据库故障返回 500，不伪装成未登录 401。
- 浏览器刷新遇到网络、429、5xx 时不立即清除登录状态。
- 注册增加确认密码和验证码加载状态。
- 个人资料错误显示结构化信息。
- Antigravity Token 按账号隔离，清理旧 project 缓存。

#### 支付、兑换和站点销售

- 支付宝补偿复用已有待支付补单状态机。
- 易支付上游 type 支持点号，但本地支付类型校验不放宽。
- 续费弹窗在手机端可滚动，保持包豪斯硬阴影。
- 订单兑换码必须匹配订单、用户、金额、类型和单次使用规则，并在行锁内再次校验。
- 公共兑换失败使用 Redis Lua 固定 10 分钟窗口，不因每次失败无限续期。
- 支付履约和管理员可信发放不增加公共失败次数。
- 站点可以选择“充值+订阅”“仅充值”“仅订阅”的销售入口；已购买权益、管理员页面和历史记录仍保留。

#### 价格和用量

- DeepSeek Flash/Pro、GLM-5.3/Flash 价格和切换时刻修复。
- 成本明细显示精度提高，但不改变真实扣费精度。
- Token 请求统计覆盖所有平台，不只 OpenAI。
- Ops 错误详情默认把时间和错误内容放到前面。
- 用户批量删除增加确认，失败项保持选中。
- 隐私/账号检查客户端使用 Firefox 配置，增加 Cloudflare challenge 的安全提示，但不承诺绕过所有 Cloudflare。

### 10. 包豪斯界面变化

没有退回上游默认皮肤。新增页面使用现有设计：

- 直角边框；
- 仪表盘同源硬阴影；
- 红黄蓝重点色；
- 自研 Toggle/Select/对话框；
- 手机端不横向溢出；
- 深浅主题、中英文、焦点、禁用、按压和减少动画状态。

本批重点是后台能力，不是重新改首页布局。

## 第三部分：和两个上游仍然不一样的地方

### A. TokenRouter 上游还有，但当前版本没有同步的内容

#### 1. 完整 Codex pinned manifest / 模型代理

上游曾经加入过按固定 OAuth 账号发现 Codex 模型清单的完整代理方案，后续又撤回了相关代理路由。

ByteSeek 没有恢复它，只保留本地已有的账号模型同步和可见模型目录。

原因：

- 完整 manifest 方案会引入一套新的缓存、账号选择和模型元数据链；
- 容易绕过本地号池、分组白名单和调度资格；
- 上游已经撤回，恢复旧方案没有稳定最终意图；
- 现有模型发现已经能满足管理端和网关目录需求。

#### 2. 独立 channel-monitor 模块

上游有一组独立的 channel-monitor V1/V2 更新，包括刷新间隔、UTC bucket、用户排行开关和 MiniMax allowlist。

ByteSeek 没有恢复整套模块，因为当前 fork 没有对应的模块边界、表结构和任务体系。强行复制会带入新的监控数据模型，可能和现有质量检测、Usage、Ops 统计重复。

ByteSeek 只保留了能直接落到现有 Ops/Usage 结构的统计修复。

#### 3. 默认连接池五倍系数

上游建议 ctx pool 默认容量系数为 5。ByteSeek 没有改成 5 倍。

原因：你是多账号中转池，直接放大每账号连接数会增加上游连接、内存和并发压力，也可能改变已有调度。当前保留原 fork 的池容量和动态配置。

#### 4. 上游运营/部署周边

部分 Apple Container 网络、插件 ZIP 细节、custom-page 拖拽按钮、独立监控日志策略等没有全部照搬。

原因：它们和 ByteSeek 的部署方式、页面结构或现有运维模块不是同一个边界；没有直接收益就不引入额外行为。

#### 5. 已撤回或用户明确不要的功能

- Codex Metadata 补齐实验；
- Bearer Token 生成 AT 并导入号池；
- 旧的 billing probe/账号站点倍率探测；
- 已撤回的旧功能实现。

这些即使上游存在，也不会换一个来源重新引入。

### B. sub2api 上游还有，但当前版本没有同步的内容

#### 1. 上游完整 pinned manifest 体系

原因和 TokenRouter 部分相同：会改变账号池模型发现、缓存和调度边界，而且上游相关代理后来撤回。ByteSeek 使用自己的可见模型目录和账号配置模型列表。

#### 2. 独立 channel-monitor / monitor-v2 全套

ByteSeek 没有相同模块和迁移，不能只复制前端开关。若以后要同步，需要先设计数据表、bucket、任务租约、与现有质量检测的关系，再单独评估。

#### 3. 上游 Composite/旧监控迁移

MiniMax/OpenCode 迁移只扩展 ByteSeek 真实存在的额度表约束，编号改成 273/274；没有恢复已经删除的 Composite、旧监控表或上游原始迁移文件。

原因：原样迁移会和当前数据库结构、账号池语义冲突。

#### 4. sub2api 的全套站点运营界面

ByteSeek 只吸收了站点销售模式的后端和必要设置，保留已购订阅、历史、管理员管理和旧支付行为；没有照搬“关闭订阅就隐藏所有订阅入口”的整页行为。

原因：销售入口开关不能等价于删除已购权益，也不能影响号池正在使用的订阅。

#### 5. 其他没有证据的模型元数据

没有把上游看到的模型名称自动当成价格、上下文、图片能力或官方额度。

原因：错误元数据会造成错误计费、错误可用性或误导用户。没有可靠来源的字段保持未知或使用本地已有配置。

### C. 当前版本和上游的实现差异，但不是缺功能

这些是有意适配，而不是漏同步：

| 主题 | 上游做法 | ByteSeek 做法 | 原因 |
| --- | --- | --- | --- |
| 模型白名单 | 可能重命名旧展示列表并直接启用 | 新增独立 `model_allowlist`，默认关闭 | 不破坏旧展示列表和旧调用 |
| 迁移编号 | 上游使用原编号 | 从本地 270 后改为 271–274 | 防止和已发布迁移冲突 |
| Composite | 上游模型/监控边界不同 | 保留本地复合 Key、订阅和多平台语义 | 账号池权限不能被覆盖 |
| 图片 | 上游路径更集中 | Image 1.5/2/2.5 按本地入口和计费边界适配 | 不改变原有计费/创作台生命周期 |
| 订阅批处理 | 上游有自己的缓存/数据模型 | 逐用户事务、旧套餐时间链、强幂等键 | 保证已有订阅不被覆盖 |
| 登录刷新 | 上游更简单 | 保留本地跨标签页刷新和换号保护 | 中转站多用户场景需要会话稳定 |
| 视觉 | 上游默认 UI | ByteSeek 包豪斯 UI | 长期 fork 设计约束 |

## 第四部分：为什么没有把所有上游代码直接合并

简单说，原因不是“代码冲突”，而是业务边界不同：

1. 你的项目是多账号中转站，最重要的是账号调度、额度耗尽切换、会话隔离、计费和 Key 权限不能被破坏。
2. 上游有些功能是给单站点、单账号或另一套监控数据结构设计的，直接搬过来会出现重复缓存、重复扣费或模型权限绕过。
3. 有些上游提交是“处理标记”或后来撤回，不代表最终功能仍然应该存在。
4. 视觉层必须保持包豪斯，不能为了减少合并冲突把上游默认页面覆盖回来。
5. 没有可靠模型价格、上下文、额度证据时，宁可显示未知，也不能虚构一个价格或把账号显示为可用。

## 第五部分：当前版本对账号池的实际影响

对多账号中转最关键的结论：

- 账号额度耗尽后仍按原调度链切换账号。
- 质量检测为降智/失败的账号继续可以被停调，不会因为模型目录更新自动恢复。
- Key、用户、线程和 WS 会话隔离规则保留。
- 复合 Key 的前缀、订阅分组和模型白名单会在正确的最终分组上重新检查。
- 订阅批量分配不会覆盖已有同套餐时间链，会追加 pending。
- 结算幂等和已有账单不会因为新模型/新平台回写。
- 新平台和白名单默认不会改变旧账号的可用行为，除非管理员主动配置。
- 新增迁移 271–274 需要升级时按顺序执行，不能删除旧迁移。

## 第六部分：目前还没有验证的事情

以下不是“没有同步”，而是本地合成测试没有替代真实环境：

- 真实 OpenAI、MiniMax、OpenCode 账号的长期生产请求；
- 真实额度耗尽后的跨账号切换压力；
- 真实外部支付回调和高并发订单；
- 生产数据库规模下迁移和索引耗时；
- 所有浏览器和所有代理/TLS 网络环境；
- 官方 Cloudflare 质询是否在你的服务器网络下完全消失；
- 模型上游临时 overload、429、网络断开等真实故障的长期统计。

## 最后给你的实际建议

如果你从 bh.026 升级到当前版本，最需要注意的不是 UI，而是：

1. 先备份数据库，再让 271–274 迁移按顺序执行。
2. 新的模型白名单先保持关闭，确认模型目录和号池运行正常后再逐组开启。
3. MiniMax/OpenCode 先用少量测试账号验证真实余额和上游协议，再加入大号池。
4. 批量订阅遇到“结果不明确”时，先查数据库实际订阅，不要换新幂等键盲目重试。
5. 镜像使用固定 digest 更稳：

```text
ghcr.io/sourceonece/byteseek@sha256:a69df1505fc65b9fafd3da6921398f0e7517b7ada14cfe8500830c1229f0f6be
```

## 结论

当前 bh.030 相比 bh.026，已经从“稳定的 Codex 图片/WS 网关”扩展成“多平台、多协议、带较完整管理运营能力的账号池网关”。

它不是把两个上游完整拼在一起，而是保留 ByteSeek 自己的账号池、调度、计费、订阅、TLS 和包豪斯边界，选择性吸收上游中能证明不会破坏这些边界的功能。
